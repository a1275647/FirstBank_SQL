# SQL 部署紀錄管理

本目錄以「每個部署批次一份 Markdown」記錄 SQL 在各環境的部署狀態。
SQL 腳本與部署狀態分開管理，避免為了更新人員、日期或申請單號而修改 SQL。

## 建議流程

1. 建立日期批次 SQL，並在同一次變更中同步更新 root 層物件定義。
2. 首次交付任何環境後，凍結該日期批次的 SQL。
3. 每次部署都在對應的批次文件補上環境、日期、人員、commit、checksum 與結果。
4. 已部署批次若需要修正，建立新的日期批次，不回頭覆寫原始 SQL。
5. 正式機交付前，固定候選 commit 與每份 SQL 的 SHA-256。
6. DBA 執行後，補上申請單號、執行資訊與實際結果。

## 狀態用語

| 狀態 | 說明 |
|---|---|
| 待提報 | 尚未建立申請單 |
| 待核准 | 申請單已建立，等待核准 |
| 待執行 | 已核准，等待執行 |
| 執行成功 | 已完成且驗證通過 |
| 執行失敗 | 執行或驗證失敗，尚未回復 |
| 已回復 | 已完成 rollback 或其他復原措施 |
| 已部署（版本待補） | 已確認部署，但缺少 commit、checksum 或執行證據 |

## 每批次必要欄位

- 批次名稱與候選 commit
- SQL 路徑及 SHA-256
- 公司測試機、甲方測試機、甲方正式機的狀態
- 實際執行日期與執行人
- 實際部署 commit 或交付包 checksum
- 正式機申請單號
- 執行及驗證結果

## 維護原則

- 不確定的資料填寫「待補」，不可推測。
- 測試機與正式機若使用不同版本，必須分別記錄 commit 與 checksum。
- 狀態更新應透過獨立 Git commit 提交，以保留完整時間線。
- 批次文件中的執行紀錄採追加方式維護，不刪除既有紀錄。
